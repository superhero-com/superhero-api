# Profile images API

Website and native clients share the JSON-only `/api/profile-media` protocol. Image bytes upload directly to private object storage using the Shorts `direct-s3-v1` encryption format. A separate image worker compresses and pins validated images to IPFS; the dedicated `/profile-images` edge delivers them. Image blobs never pass through the application API. Images become public after technical validation and a wallet-authorized AddressLink transaction. Nostr profile pictures are independent.

`GET /config` advertises availability, network, AddressLink contract, origin, dimensions and upload limit. Clients must reject network and origin mismatches. `GET /batch?addresses=ak_...,ak_...` resolves up to 50 accounts from canonical chain state with a 15-second cache. It returns portable `avatar_ref`, `avatar_preview_ref`, `cover_ref` and `cover_preview_ref`, plus `avatar_cid` and `cover_cid`. The legacy `avatarurl`, `avatar_thumbnail_url`, `coverurl` and `cover_thumbnail_url` fields remain resolved HTTP URLs for older clients. Empty URLs mean use the address-derived fallback. Public profile reads include these fields when enabled.

## Wallet session and direct uploads

1. `POST /auth/challenge` with `{address}`. Verify the message's address, origin, network, contract, nonce and expiry against the advertised configuration before signing it with the AE signed-message convention.
2. `POST /auth/verify` with `{id, signature}`. The one-use challenge returns a 30-minute bearer session. Keep its token in memory; use secure platform storage only if session persistence is required. `POST /auth/logout` revokes it.
3. Crop and compress locally if desired. `POST /uploads` with `{role, bytes, sha256}` reserves an upload for 30 minutes and returns `id`, `partSize` (1 MiB), `parts` (completed indices), `status` and `expiresAt`. Store the non-secret ID and source hash to resume the same file. `GET /uploads/:id` reads progress; `POST /uploads/:id/cancel` cancels an unprocessed upload.
4. For each part, `POST /uploads/:id/parts/:index/prepare` with its plaintext `{sha256}`. The response contains a scoped AES-256-GCM key, IV, base64 AAD, expected hash and size. Encrypt the plaintext using those exact parameters and a 128-bit tag. The binary envelope is ASCII `SHPRIV02`, 12-byte IV, 16-byte tag, then ciphertext. Keys apply only to that object; master keys never leave the server.
5. `POST /uploads/:id/parts/:index/authorize` with `{checksum}` containing the hex SHA-256 of that envelope. PUT the encrypted bytes directly to the returned HTTPS URL, using its method and headers. Never send the API bearer token to storage. Permissions expire within five minutes, bind size and checksum, and require create-only writes. Reauthorize the same immutable part when needed. An HTTP 412 can mean a prior PUT succeeded; verify it through the next step.
6. `POST /uploads/:id/parts/:index/complete` performs a storage HEAD check for exact size and checksum. The API does not fetch bytes. Then `POST /uploads/:id/finish` queues processing; poll the upload until `ready` (with `cid`) or `failed`. Retry an interrupted status read using the same ID.

The worker accepts JPEG, PNG and WebP still images up to 10 MiB, 24 megapixels and 8192 pixels per dimension, with a minimum side of 128 pixels. It verifies source hashes, strips metadata, normalizes orientation, crops to 1:1 or 8:3, and generates compressed WebP images and thumbnails. Avatar output is at most 1024×1024, cover output at most 1920×720; small sources are not enlarged. The browser editor also crops and compresses before transfer.

## Publishing and removal

`POST /claim` with `{role, cid}` prepares an AddressLink message. Use `cid: null` to remove a link. Only the upload owner can claim an asset. Verify the exact message `link:<address>:<role>:ipfs_superhero_images_<cid>:<nonce>` or `unlink:<address>:<role>:<nonce>` before signing.

`POST /submit` with `{id, signature}` publishes the authorized change. Persist the non-secret operation ID before submitting. Repeating the same ID is idempotent. After a timeout, check `GET /writes/:id` before starting another operation. `signed` and `submitted` are pending; `confirmed` and `failed` are terminal. The backend journals signed transactions before broadcast and rebroadcasts only the same bytes. A successful mined contract call is confirmed immediately, with no additional block wait. Background status checks run every five seconds; reverted calls fail and a missing receipt stays pending. A stale AddressLink nonce requires a new claim and signature.

To recover after reloading or session expiry, poll `GET /writes/:id/status?address=ak_...` using the saved random operation ID and wallet address. This rate-limited, uncached read requires no session and returns only `{id, role, status}`. It does not reveal unpublished image references or trigger a transaction. Clear the saved operation only after a terminal status; retain it on network errors and offer a retry. The detailed `/writes/:id` route and all upload and publication actions still require a wallet session.

`GET /profile-images/images/:cid/image.webp` and `/thumb.webp` are served by the separate image edge, with a 60-second cache lifetime. Only known, published catalog assets are served. Arbitrary CIDs, remote URLs and original files are unavailable. Each IPFS directory contains the normalized image, thumbnail and a manifest binding owner, role, network and contract. This avoids collisions between wallets under AddressLink's provider-level uniqueness constraint. New links store `ipfs_superhero_images_<cid>` in the `avatar` or `cover` provider collection. Existing bare-CID links remain supported, including retention checks and pending pre-upgrade signatures. Unlinking does not erase public blockchain history or downloaded bytes.

## Runtime configuration

Apply `ProfileMedia1792954800000`, `ProfileMediaCleanup1793008800000` and `PostImages1793012400000` before enabling the module. Configure `PROFILE_MEDIA_ENABLED=true`, `AE_NETWORK_ID`, `PROFILE_MEDIA_CONTRACT`, `PROFILE_MEDIA_NODE`, `PROFILE_MEDIA_ORIGIN`, `PROFILE_MEDIA_PUBLIC_URL` (the dedicated `/profile-images` base), `PROFILE_MEDIA_IPFS_API`, `PROFILE_MEDIA_IPFS_TOKEN_FILE` and `PROFILE_MEDIA_PROVIDER_KEY_FILE`. IPFS values can fall back to `SHORTS_IPFS_*`. Direct storage uses the existing `SHORTS_PRIVATE_S3_*` configuration and encryption key ring, with a namespace derived from network and `PROFILE_MEDIA_STORAGE_CONTRACT` (defaults to the AddressLink contract). An existing Shorts storage contract may be selected to reuse its authorized namespace; profile object IDs always have a `profile-` prefix and are independent of Shorts records. This storage identity must remain stable while uploads exist. Ensure storage policy allows the selected namespace and CORS allows the website origin. Credentials are backend-only files with mode 0600.

Run the image worker/edge independently using `node dist/profile-media/worker-main.js`, with its port set by `PROFILE_MEDIA_PORT` (default 3336). Route `/profile-images/` directly to that service. Give it object-storage and IPFS credentials, but do not mount the provider signing key. The key path remains a configuration field; this process never reads it. The main API owns wallet sessions, metadata and chain writes; it does not instantiate the decoder, IPFS storage or edge. The worker needs platform-specific Sharp packages and bounded process memory/CPU.

The Nest operations entry point is `node dist/profile-media/operations-main.js key|status|register`. `key` exclusively creates or validates the configured credential and prints only its public address. `register` enrolls `avatar` and `cover` after checking ownership; ownership is immutable. Runtime startup verifies ownership and never registers automatically. Fund the dedicated provider only for sponsored profile writes.

The normalized-image catalog reserves at most 256 MiB by default. Raw upload reservations are capped separately at half that budget, including abandoned uploads and encrypted-envelope overhead accounted for by the storage layer. `PROFILE_MEDIA_MAX_STORED_BYTES` sets a budget from 1 MiB to 1 GiB. New uploads stop when either budget is full. Successful cleanup releases the corresponding reservation. Reads and existing links remain available.

Replaced images become eligible for automatic cleanup after one minute; unused prepared images expire after 24 hours. Every 30 seconds the API checks uncached AddressLink state, serializes against provider submissions, and protects pending claims and uploads before disabling an obsolete catalog entry. The separate image worker journals its exact IPFS block list, unpins that directory, and removes only its unreferenced blocks. Blocks pinned by another image or Short are retained; repository-wide garbage collection remains disabled. Interrupted deletions retry from the journal. Re-uploading a deleted image restores and repins its catalog entry. Image saves still finish at the successful mined transaction, independently of cleanup.

The worker also deletes encrypted temporary parts after an upload has expired for one hour and processing has ended. Current normalized images do not depend on these originals. Mount a separate worker-only credential through `PROFILE_MEDIA_CLEANUP_S3_CREDENTIALS_FILE`, granting `s3:DeleteObject` and `s3:DeleteObjectVersion` only on the active storage namespace’s `profile-*/direct-part/*` keys and `s3:ListBucketVersions` restricted to that prefix. The `cleanup-policy` operations command emits that scoped IAM policy. Cleanup removes all versions and delete markers of each exact temporary key, verifies their absence, and also supports unversioned null versions. The shared Shorts object service exposes no deletion method. IPFS must support authenticated writer-only `refs` and `block/rm` with the bounded options enforced by the storage gate. Deleted records retain the transaction and deletion journal, but no longer reserve image capacity. Public chain history and copies downloaded elsewhere cannot be erased.

Processing uses one job per worker and two shared admission slots, durable leases, at most three attempts, per-wallet/service rate limits, and isolated decoders. Database pools, file sizes, decoding time and upstream requests are bounded separately.

Run `node -r ts-node/register -r tsconfig-paths/register --test src/profile-media/profile-media.test.cjs`. Set `PROFILE_MEDIA_TEST_DATABASE_URL` to a disposable loopback PostgreSQL database ending in `_test` for HTTP, direct-transfer, ownership, journaling, worker recovery and quota tests. Each run creates and removes its own schema. Chain and object/IPFS transports are mocked; verify actual provider transactions and storage in the target environment as well.

For a new testnet deployment, `deploy` accepts `PROFILE_MEDIA_DEPLOY_ARTIFACT` (an absolute compiler artifact path containing bytecode and the exact supported ACI) and `PROFILE_MEDIA_DEPLOY_JOURNAL_FILE` (an absolute private journal path). It records signed deployment bytes before broadcasting and reuses that transaction on retry. It refuses mainnet deployment and artifact/account/network mismatches. Verify deployed bytecode and a standard wallet-signed dry run before selecting a contract; addresses in older documentation may refer to incompatible signature verification. Register both providers after deployment is mined.

## Portable images and previews

New post media entries and avatar/cover API references use `ipfs:superhero:images:<cid>`. The corresponding preview is `ipfs:superhero:images:<cid>-preview`. This is a Superhero reference namespace, not an HTTP URL or a native browser IPFS URL. The CID identifies the immutable directory containing both `image.webp` and `thumb.webp`; the suffix selects the thumbnail. One base CID therefore commits both variants. Do not insert the preview as a second attachment or create an extra profile transaction. The AddressLink contract rejects colons in values, so new avatar/cover links and signatures use `ipfs_superhero_images_<cid>` on-chain. `/claim.value` is that exact underscore reference; `/claim.reference` and profile reads expose the colon-based full/preview namespace. `/config.references.profileLinkPrefix` advertises the on-chain prefix. Existing bare-CID links still resolve and remain protected from cleanup. A bare-CID signature prepared before the update is submitted unchanged; new claims use underscores. This preserves existing identity links and domain independence without migrating the contract.

Resolve a base reference to `<publicUrl>/images/<cid>/image.webp` and a preview to `<publicUrl>/images/<cid>/thumb.webp`, using `GET /config`'s `publicUrl`. HTTP host and prefix are deployment configuration, not image identity. The website uses `VITE_PROFILE_MEDIA_PUBLIC_URL` (default: its profile API origin plus `/profile-images`); the SEO service uses `PROFILE_MEDIA_PUBLIC_URL`. Changing the delivery location does not require changing on-chain references. Never accept arbitrary suffixes or concatenate unvalidated reference data into a path.

For posts, authenticate with `purpose: post`, then use the same direct upload protocol with `role: post`. It accepts 1–4 images, including an empty caption. `POST /attachments` with `{cids}` verifies ownership and availability, retains the directories before the post signature, and returns `media` (base references, in request order) plus `previews` (matching preview references). Send only `media` as the Tipping contract's attachments; replies retain the existing `comment:<id>` marker. As before, cancelling after retention may leave an unused but retained directory, protecting immutable posts from client disappearance.

Post display images preserve aspect ratio within 2048×2048, at WebP quality 84. Avatar/cover display images use quality 88. All previews start at quality 68, with maximum dimensions 128×128 for avatars, 480×180 for covers and 640×640 for posts. Detailed inputs use lower quality/dimensions as needed to stay at or below 48 KiB. Neither variant enlarges small source images; both strip source metadata. Feed cards fetch the preview, and opening a gallery fetches the larger image. The browser compresses/resizes before encrypted direct transfer; image blobs still never pass through the Superhero application API.

Existing on-chain HTTP URLs cannot be rewritten. The website recognizes previously issued superhero.stream catalog URLs and resolves them through its current delivery configuration, using their stored thumbnail in feeds. Existing external GIF/video URLs still render. Existing packages are immutable and keep their original encoder settings; the tighter preview bound applies to new uploads. Old and new avatar/cover links use the same CID-based ownership and cleanup protections.
